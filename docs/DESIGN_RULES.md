# Design Rules

**Project:** Campus Sustainability & Issue-Response Platform
**Repository:** `campus-issue-platform`
**Status:** Active — these rules apply from first commit onwards
**Last Updated:** 2026-09-20

> These rules govern all development work on this project — whether written by a human developer or generated by an AI coding assistant. Any proposed deviation must be explicitly discussed and approved before implementation.

---

## Rule 1: Do Not Build Features Outside the PRD Without Approval

- Only implement features that are described in `docs/PRD.md` or have been explicitly approved in writing (e.g., in a GitHub issue or documented decision).
- If you think a feature is needed but it is not in the PRD, document the proposal first. Do not build it speculatively.
- Scope creep is the primary risk to this project. When in doubt, do less.

---

## Rule 2: Do Not Add Unnecessary Dependencies

- Every added library or package must have a clear, documented reason.
- Do not install a package because it seemed convenient or was suggested by an AI assistant.
- Before adding a dependency, ask: can this be done with something already in the project?
- Dependencies must be pinned to specific versions in `requirements.txt` or equivalent.
- Development-only dependencies must be separated from production dependencies.

---

## Rule 3: Do Not Introduce Paid Services Without Explicit Approval

- All required services must have a free-tier or self-hosted option.
- If a tool, API, or service requires payment for the features needed, flag it before using it.
- No API key, subscription, or credit card should be required to run the project locally.
- Examples of free/open-source alternatives to prefer:
  - LLM: Gemini free tier, Ollama local models
  - Embeddings: `sentence-transformers` (local)
  - Object storage: MinIO (self-hosted) instead of AWS S3
  - Vector store: ChromaDB (local)

---

## Rule 4: Do Not Expose Secrets or API Keys

- No API keys, passwords, tokens, or credentials may appear in source code.
- No secrets may be committed to Git under any circumstances — including in comments, test files, or documentation.
- All secrets must be managed via environment variables loaded from `.env` files.
- `.env` files must be listed in `.gitignore` before the first commit.
- A `.env.example` file (with no real values, only key names) must be maintained.
- If a secret is accidentally committed, treat it as compromised and rotate it immediately.

---

## Rule 5: Do Not Use AI for Final Safety Decisions

- AI classification output is an input to the system, not the final authority.
- `app/core/safety_rules.py` is the authoritative source for safety classification.
- The safety rules module must be called after every AI classification call.
- An AI suggestion that conflicts with a safety rule must be discarded. The rule wins.
- This is non-negotiable regardless of the LLM's confidence score.

---

## Rule 6: Do Not Provide Unsafe Repair Instructions

- For any issue in a safety-critical category (ELECTRICAL, FIRE_SAFETY, or any keyword-triggered flag), the system must:
  - Show a safety alert
  - Direct the user away from the hazard
  - NOT provide any instructions that imply the user should interact with the hazard
- Quick action suggestions are only permitted for issues where safety rules have confirmed no critical hazard.
- When in doubt, the system defaults to a safety alert. Never default to a quick action.
- This rule applies to LLM-generated output, template text, and all other response types.

---

## Rule 7: Follow Accessibility Requirements

- All UI elements must be usable with a mobile browser.
- Tap/click targets must be large enough to use comfortably on a touchscreen.
- Do not rely on hover states as the only interaction affordance.
- Text must be readable without zooming (minimum 16px body text equivalent).
- Color must not be the only indicator of status or severity (use text labels alongside color).
- Error messages must appear near the relevant form field, in plain language.
- Forms must work without JavaScript where feasible.
- Do not add loading animations or transitions that have no functional purpose.

---

## Rule 8: Keep the UI Simple

- The application must not look like a generic AI-generated student project.
- Do not add features to the UI to make it look impressive — add them only because users need them.
- Avoid:
  - Decorative animations
  - Redundant visual elements
  - Feature showcases that are not useful to the primary user
  - Technical jargon in user-facing text
  - Complex multi-step forms when a simpler flow achieves the same result
- Every UI element must earn its place. If you cannot explain why a user needs it, remove it.

---

## Rule 9: Preserve Existing Functionality When Modifying Code

- Before modifying a file or function, understand what it currently does and who depends on it.
- Do not refactor working code unless the refactor is explicitly planned and approved.
- If a change breaks existing behavior, the change is incomplete until the breakage is fixed.
- Any change to a shared utility, model, or service must be traced to all callers.

---

## Rule 10: Test Before Declaring a Feature Complete

- A feature is not complete unless it has been manually verified to work end-to-end.
- For backend endpoints: test with a real HTTP client (e.g., curl, Postman, or a test script).
- For AI-related features: run at least the test cases defined in `docs/AI_DESIGN.md`.
- For UI features: test on both a desktop browser and a mobile-sized viewport.
- Document what was tested and what the result was before marking a task as done.

---

## Rule 11: Never Claim Something Works Without Testing It

- Do not write in commit messages, comments, or documentation that something "works" unless it has been run and verified.
- If a feature has only been written but not run, say so explicitly.
- If a feature is partially implemented, mark it as such.
- Unverified output from an AI coding assistant is a draft, not a working implementation, until tested.

---

## Rule 12: Keep Code Modular and Documented

- Each module must have a single, clear responsibility.
- Functions and classes must have docstrings that explain their purpose, parameters, and return values.
- Business logic must not be embedded inside route handlers. Route handlers call services; services contain logic.
- The AI layer (`ai_service.py`), safety rules (`safety_rules.py`), and priority logic (`priority.py`) must remain separate modules and must not be merged.
- If a file exceeds approximately 300 lines, consider whether it should be split.

---

## Rule 13: Use Git Commits After Verified Milestones

- Do not commit unverified or partially broken code to `main`.
- Use feature branches for development.
- Commit messages must describe what changed and why, in plain language.
- A commit message like "fixes" or "update" is not acceptable.
- After verifying that a feature or fix works, commit with a descriptive message before moving to the next task.
- Tag significant milestones (e.g., `v0.1-mvp-backend`, `v0.2-ai-pipeline`).

---

## Rule 14: Document Assumptions

- If you implement something where the specification is ambiguous, document the assumption in code comments and in the relevant doc file.
- Do not silently expand scope to fill an ambiguity.
- If an assumption is later found to be wrong, update both the code and the documentation.

---

## Rule 15: Responsible AI Requirements Are Non-Negotiable

The following are hard constraints, not guidelines:

| Constraint | Detail |
|---|---|
| No face recognition | Do not use any face detection or recognition feature under any circumstances |
| No personal profiling | Do not collect or infer personal attributes from user behavior or reports |
| No student surveillance | The system must not track user locations, movements, or activity beyond what is needed for issue reporting |
| Photo retention | Photos must be deleted after AI processing unless retained for audit of safety-critical reports. Audit retention must be time-limited and access-controlled. |
| Data minimization | Collect only what is necessary. Do not add fields to capture extra data "just in case." |
| AI transparency | Users must be informed when AI has contributed to a response or classification |
| Source attribution | RAG-retrieved information must be labeled with its source |
| Human control | No AI output may take effect on a safety classification without passing through `safety_rules.py` |

---

## Rule 16: No Chatbot Design

- The main user experience must not be conversational.
- Do not add a chat interface, a floating AI assistant, or a conversational flow to the main reporting workflow.
- AI output appears as structured responses (quick action or safety alert) tied to a specific report, not as a conversation thread.
- If a future feature proposal involves a chat interface, it must be presented to the team as a significant design decision before any implementation begins.

---

## Checklist: Before Opening a Pull Request

- [ ] Feature is described in the PRD (or approved as an addition)
- [ ] No new paid dependencies introduced
- [ ] No secrets in the code or commit history
- [ ] Safety rules are not bypassed
- [ ] Responsible AI constraints are not violated
- [ ] Feature has been manually tested end-to-end
- [ ] Existing tests still pass
- [ ] Code is documented (docstrings, inline comments where non-obvious)
- [ ] Commit messages are descriptive
- [ ] `.env.example` is updated if new environment variables were added
